# GPU 高负载生产性能实验计划

**2026-10-20 · 待执行 · RTX 5090 32,607 MiB / 28 CPU / 94 GiB RAM**

## 0. 计划结论

本计划测出持续 GPU 利用率 30% / 50% / 70% / 85% 下的生产吞吐、尾延迟与数据质量，给出安全工作点，并用一次 100 条生产验证确认该工作点。

高负载由两条路径产生：

- **A 真实共租**：被测作业 + 0/1/2/3 个同任务生产进程，模拟多作业共享 GPU；
- **C 合成填充**：被测作业 + 小显存 CUDA 负载，闭环把利用率按在目标档位。

A 给出真实多作业场景，C 给出同一利用率的干净对照。两者在同一利用率分箱内的差异用于研究 CPU、IO 与调度争用；利用率匹配不能隔离所有 GPU 争用因素，仍需结合功耗、时钟与进程观测判断。


24 环境准入被内存阻塞（要求 144 GiB，可用 93.44 GiB），本轮高负载实验按 4 环境设计，8 环境作为单点参考。

## 2. 高负载的定义

- **持续利用率**：单元内去除前 60 秒后的生产窗口（至少 2 分钟）均值达到目标档位，p50 不低于目标 −5%；70% 与 85% 档另做 10 分钟稳态复测。
- **档位**：30% / 50% / 70% / 85%；70% 与 85% 为高负载档，30% 与 50% 为低/中载基线。
- **功耗与降频**：每档记录功耗、SM 时钟、温度与 throttle 原因；85% 档触发降频时标记为“功耗受限”，与“算力争用”分开分析。
- **观测数**：每档 3 个 seed × 2 个重复 = 6 个观测；确认阶段用未参与探索的 seed 404/505 复测。

## 3. 设计与矩阵

被测作业固定：OpenArm 左臂、4 环境、每格 4 次尝试、final-hold 60、seed 101/202/303。

基线：4 环境固定预算 0.94–1.30 条/分；8 环境 1.682 条/分（7/8 成功，4 workers，见前置实验）。矩阵以 4 环境为主，8 环境作为单点对照。

| 臂 | 负载档位 | 导出模式 | seed | 重复 | 单元数 |
|---|---|---|---:|---:|---:|
| A 真实共租 | 0/1/2/3 个共租进程（目标 30/50/70/85%） | sync / auto | 3 | 2 | 48 |
| C 合成填充 | 30/50/70/85% 闭环 | sync / auto | 3 | 2 | 48 |
| B 渲染加重（可选） | 1/2/3 路相机或 640×480/960×720 | auto | 3 | 2 | 18 |

A 与 C 是主实验，合计 96 个单元；B 用于回答“提高单条数据渲染负载是否值得”，单独成臂。

A 臂的进程数是粗调，C 臂的合成填充是细调；档位按校准后的实际利用率分箱，不按进程数硬分。

每单元 4 次尝试，主实验共 384 条被测轨迹；按 5–8 分钟/单元，约 10–13 GPU 小时。

## 4. 控制变量

固定：任务 YAML、输入源 SHA256、4 环境、4 次尝试、final-hold 60、导出队列 16 GiB、驱动 595.91.07、同一张卡。

按单元记录并控制：

- **CPU**：28 核。被测进程 `taskset -c 0-13`，共租进程 `taskset -c 14-27`；每进程 CPU 利用率单独记录。绑核基线单独测一次；与不绑核差异超过 10% 时，以绑核基线为准并在结果中注明。
- **GPU 时钟**：权限允许时 `nvidia-smi -lgc 2400` 锁定 SM 时钟；结束后恢复。权限不允许时，记录 clocks.sm 作为协变量。
- **顺序**：每个重复块内随机化档位与导出模式，sync/auto 交替，避免固定顺序。
- **隔离**：每单元前用 `nvidia-smi pmon` 确认无其他 GPU 计算进程；共享队列串行执行；共租进程使用独立目录、独立 run ID、独立 telemetry/export 命名空间。
- **温度**：每单元前冷却 60 秒，记录起始温度。

## 5. 测量与校验

### 5.1 仪表

主机没有 DCGM 与 pynvml，使用 `nvidia-smi` 原生接口：

| 信号 | 采集 | 频率 |
|---|---|---|
| GPU 利用率、显存、功耗、温度、SM/MEM 时钟 | `nvidia-smi --query-gpu=timestamp,utilization.gpu,memory.used,power.draw,temperature.gpu,clocks.sm,clocks.mem --format=csv -l 1` | 1 Hz |
| 每进程 SM/显存 | `nvidia-smi pmon -s um -d 1` | 1 Hz |
| 功耗/温度/时钟汇总 | `nvidia-smi dmon -s pucvmet -d 1` | 1 Hz |
| CPU、RSS、IO | cgroup 与 `pidstat -p <pid> 1` | 1 Hz |
| 阶段耗时 | AutoData 既有 `telemetry.jsonl` | 事件级 |
| 磁盘与队列 | `df`、队列状态 | 10 s |

`utilization.gpu` 是“有 kernel 在跑的时间占比”，不是 SM 占用率；结果同时报告功耗、SM 时钟与 pmon，用这三项区分“算力争用”与“降频”。

### 5.2 闭环控制器（C 臂）

2 Hz 读取 10 秒滑动平均 GPU 利用率，PID 调整合成负载的忙闲占空比或批大小，把利用率按在目标 ±5%。日志记录 setpoint、实际值与控制器输出。

A 臂不使用闭环控制器：档位就是共租进程数，实际利用率作为结果记录。A 的利用率是多作业共租的自然结果，C 是精确控制的对照。

### 5.3 生产与校验

- 被测作业用 `produce.py` 只生产、不校验，输出独立目录；共租作业同任务、不同 seed，只提供负载。
- 每单元结束后离线校验被测输出：HDF5 回读、严格终态、逐数组哈希、图像有效性。
- 主指标同时给两种：**仿真终态接受吞吐**与**独立校验合格吞吐**；校验耗时单列。
- 校验使用现有 `validate_output.py` 的严格终态谓词，阈值不因高负载放宽。
- 图像有效性按相机检查黑帧比例与均值/方差；右腕历史 100% 疑似黑帧，作为门槛，不进入训练输入。

## 6. 指标与判定

**主指标**

- 仿真终态接受导出 / 最终文件就绪分钟；
- 独立校验合格导出 / 最终文件就绪分钟。

**次级**

- 最终文件就绪秒数、p50/p95 episode 秒数、导出等待、队列等待；
- 生产窗口与稳态复测窗口的 GPU 均值/p50/p95、显存峰值、功耗均值、温度峰值、SM 时钟均值；
- CPU 利用率、RSS 峰值；
- 严格终态通过率、HDF5 回读通过率、图像有效性（均值/方差/黑帧比例）、失败分类；
- 重复间变异系数、OOM/SIGKILL 次数。

**分析**

1. 吞吐对实际利用率做分段回归，找拐点，给 95% bootstrap 区间。
2. 每档内 sync vs auto 配对比较，报告利用率 × 导出模式的交互。
3. 在同一实际利用率分箱内比较 A 与 C；差异用于调查非 GPU 争用，并结合时钟、功耗和负载类型排除其他解释。
4. p95 与变异系数对利用率作图；p95 在拐点前翻倍时，以 p95 为准。
5. 终态合格率与图像有效性对利用率作图；出现下降即转入内存与质量调查。

**工作点判定**

推荐满足以下全部条件的最高档位：

- 吞吐 ≥ 30% 基线的 90%；
- p95 ≤ 基线的 2×；
- 严格终态与校验合格率不下降；
- 零 OOM、零 SIGKILL。

A 与 C 在匹配利用率下差 >10% 时，优先调查 CPU、IO、线程与队列，同时检查 GPU 内存带宽、kernel 组成和功耗差异；补充证据后再归因。

## 8. 安全边界

- 单进程 RSS > 44 GiB、显存 > 28 GiB、effective available < 8 GiB、温度 > 85 °C、功耗 > 600 W、磁盘 < 70 GiB：立即停止本单元。
- 任何 OOM 或 SIGKILL：保留现场，记录档位与进程组合，不重试同一单元；换新输出路径。
- 先杀共租进程，保留被测输出；每单元独立目录，不复用。
- 实验期间不运行其他 GPU 任务；队列串行。
- 24 环境准入要求 144 GiB 有效内存；当前 93.44 GiB，本轮不启动 24 环境。
