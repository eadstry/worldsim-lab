# OpenArm 单臂 SkillGen：cuRobo v2 最小可行性验证

版本 v001；实验与材料截止：2026-10-14 17:13（Asia/Shanghai）。仅本地交付。

## 结论

**v2 已在独立环境完成真实 GPU 端到端 SkillGen 验证：5 次尝试成功 4 次，10 次 transit 规划请求全部成功。当前配置暂不适合替代 v1 默认路径。**

同一组初始状态下，v1 成功 5/5。v2 后续规划请求中位数增加约 74%，整个模拟进程显存采样峰值仅减少约 1.2%；PyTorch allocated 峰值减少约 60%，但这不等于整个 planner 或进程的总显存减少 60%。小样本不能证明普遍的成功率退化或等价，当前结果也没有提供切换默认环境的充分依据。

原 `autodata` v1 环境没有进行安装、卸载或升级操作；535 个受保护文件的 SHA-256 和原已安装发行包集合均保持不变。上游子模块没有改动。所有 v2 适配、运行输出和缓存都放在独立 workspace overlay 下。

## 1. 实测结果

| 指标 | v1 | v2 | 本批观察 |
| --- | ---: | ---: | --- |
| 完整抓取放置任务成功率 | 5/5，100% | 4/5，80% | v2 的 seed 105 执行失败 |
| 任务成功率 Wilson 95% 区间 | 56.6%–100% | 37.6%–96.4% | 每版仅 5 次，区间很宽 |
| 完整 transit 请求成功率 | 10/10 | 10/10 | 规划成功不等于任务成功 |
| 后续请求耗时 p50 | 0.753 s | 1.312 s | v2 +74.2% |
| 后续请求耗时 p95 | 2.217 s | 1.764 s | v2 −20.5%，每版仅 9 个样本 |
| NVIDIA 进程显存采样峰值 | 7,284 MiB | 7,194 MiB | v2 −90 MiB，约 −1.2% |
| PyTorch allocated 会话峰值 | 140.44 MiB | 56.01 MiB | v2 约 −60.1% |
| PyTorch reserved 会话峰值 | 214 MiB | 116 MiB | v2 约 −45.8% |
| 启动到退出的总墙钟 | 949.28 s | 949.10 s | 包含模拟、渲染和录制；v2 成功样本数较少 |

“后续请求”排除每个进程的第一个完整 transit 请求，共 9 个样本。请求包含世界更新、夹爪/物体附着、多阶段规划及关节距离重采样；计时前后均做 CUDA 同步。它不是单个 IK 或 TrajOpt kernel 的耗时。

首个请求为 v1 9.343 s、v2 4.515 s。v2 在正式测试前经历了适配调试和模型预检，编译缓存状态与 v1 不完全对等，**不能把首请求差异当作可靠的冷启动性能对比**。后续请求也可能首次使用新的带物体路径，故不宣称所有内部代码路径都已完全预热。

进程显存使用 NVIDIA 每 2 秒采样，包含 Isaac Sim、渲染、cuRobo 和其他 CUDA 分配，可能遗漏瞬时峰值。PyTorch 的 allocated/reserved 统计不涵盖所有 Warp、驱动和渲染分配，不能把它们单独解释为 cuRobo 全部显存。

## 3. 版本与配置

AutoData 固定为 `1c7360d85c9ad131ca6c8c70f1f731a6312616f3`。v1 安装包显示 `0.0.post1.dev1`，仍存在旧报告所述的原始 cuRobo 来源 SHA 缺口；本次通过源文件/安装元数据哈希固定本机基线。

v2 使用独立环境与独立 OpenArm production overlay 副本，包版本为 `0.8.0.dev0+g78fd485`，固定源码提交为 [`78fd485fa82d9b9a063fb4985e371814587e666a`](https://github.com/NVlabs/curobo/commit/78fd485fa82d9b9a063fb4985e371814587e666a)。已下载的 447 个源文件与该版本引用清单中的 Git blob 哈希相符，没有修改 cuRobo 上游实现。

| 依赖 | v1 | v2 |
| --- | --- | --- |
| Python 环境 | 原 autodata，Python 3.12 | 独立副本，Python 3.12 |
| PyTorch | 2.11.0，CUDA 13.0 | 2.11.0，CUDA 13.0 |
| Warp | 1.13.0 | 1.13.0 |
| Isaac Sim | 6.0.1.0 | 6.0.1.0 |
| NumPy / h5py | 2.3.1 / 3.16.0 | 2.3.1 / 3.16.0 |
| cuda-core | 未安装 | 1.2.1 |

外层对齐的参数：32 个 IK seeds、2 个 TrajOpt seeds、最多 2 次外层规划尝试、关闭图搜索、关闭额外轨迹精调、位置容差 5 mm、旋转容差 0.05 rad、碰撞激活距离 0、关节距离采样间隔 0.005 rad、最终位姿重复 10 次。保持原有 0.05 m retreat、无额外 approach 的接触策略。

v1 使用 20 个离散轨迹步。v2 使用三阶 B-spline、16 个 knots、4 个 interpolation steps，实际 rollout horizon 为 81；输出 dense 轨迹后按相同关节距离间隔重采样。**优化表示、内部迭代和时间参数不完全等价**，这是两个集成配置的比较，不是严格等计算量的算法性能证明。v2 的原 `trajopt_tsteps` 配置标签不能当作其真实 horizon；有效配置已单独记录。

原 OpenArm 配置关闭 finetune，而固定 v2 版本的 `MotionPlanner.plan_pose` 默认会额外精调。因此适配层包装公开的 TrajOpt `solve_pose` 调用，将 `finetune_attempts` 置为 0，没有改上游文件。IK seed 对齐 v1 的默认 1531；不同版本的内部随机采样流仍不保证逐项相同。

## 4. 实现和预检实际覆盖了什么

本次沿用并完善工作区已有的独立环境准备，新增/修正了以下适配：

1. 把机器人 `ee_link` 转成 `tool_frames`，把 `retract_config` 转成 `default_joint_position`，保留原碰撞几何和关节排序。
2. 将旧世界配置与工具导入转到 v2 scene/config API；按障碍物名字更新 live cube 位姿。
3. 使用显式单位四元数构造平移 offset，匹配固定 v2 版本的 Pose 行为。
4. 使用 v2 attachment manager 拟合/附着方块，并恢复接触阶段禁用的碰撞球。
5. 通过 dense 插值轨迹取执行样本，按关节名移除锁定夹爪关节，再转为 SkillGen 所需的末端位姿序列。
6. 保留公共 episode/规划请求监控，去掉不能等价映射的 v1 内部 solver-attempt hook；v2 内部 attempt 数标为不可用，不拿 0 与 v1 比较。

GPU 模型预检实际运行并通过：活动关节是左臂 7 个关节；在默认关节配置下，GPU 正运动学与独立 URDF CPU 正运动学的变换矩阵最大元素误差为 `2.384×10⁻⁷`。这只覆盖该测试姿态，不是全关节空间的模型证明。7 项宿主测试通过，包括统计分母、模型保护、轨迹采样及锁定夹爪关节选择。

正式比较之外保留了三个中断调试运行：障碍物更新参数、平移 Pose 构造、返回轨迹的关节数映射分别暴露过接口错误，修复后重新开始完整批次。这些中断运行没有正式完成记录，未混入成功率、耗时或显存比较。工作区更早的一次 smoke 曾在另一 GPU 任务占用显存时失败，也明确排除。

## 5. seed 105 失败诊断

这是实际执行结果失败，不是规划异常。v2 该次两段 transit 请求均返回成功，HDF5 episode 的 `success=False`，动作数据完整。

对保存状态做离线读回，在原桌面坐标系重算放置条件：

| seed 105 的状态 | v1 | v2 |
| --- | ---: | ---: |
| 方块最大抬升（相对初始高度） | 104.5 mm | 8.8 mm |
| 最终桌面坐标 x / y | 0.3585 / 0.2063 m | 0.0804 / 0.2182 m |
| 方块投影轮廓是否完全在 pad 内 | 是 | 否 |
| 最终高度、夹爪释放、低速条件 | 满足 | 满足 |

pad 的 x 范围为 `[0.270, 0.485] m`，v2 方块最终明显不在其中。结合很小的抬升量，记录与漏抓相符。**规划路径、技能衔接和控制跟踪各自的因果贡献尚未定位**；不能只凭此次记录判定 cuRobo v2 核心求解器存在缺陷。失败轨迹已保留，不为提高报告成功率而删样或针对该种子调参重测。

## 7. 后续决策

保留 v1 默认环境与当前输出基线，保留 v2 为实验后端。下一步优先复现 seed 105 的漏抓，逐段比较 transit 末端到达误差、技能起点、夹爪闭合时机和实际 IK 跟踪；保持任务成功条件和源标注不变。

在解决或解释执行差异后，再以独立测试种子扩大样本，并评估 4/8 环境的显存与成功样本吞吐。当前 v2 PyTorch 分配峰值优势值得继续检查，但单环境整个进程仅节省 90 MiB；不能由此外推多环境显存比例，也不能据 5 次测试证明总体成功率相同。动力学力矩保证、批量规划和真实传感器建图均未纳入此次验证。
