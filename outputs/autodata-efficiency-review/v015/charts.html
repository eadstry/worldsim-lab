先分清保存优化和规划迁移两个问题

怎么做的

实验沿两条路线展开：先保留 cuRobo v1 规划与仿真任务，比较同步保存和异步保存；再在异步保存基础上接入 cuRobo v2。每轮记录整批文件最终就绪时间，并检查保存数据的结构和任务末态。

这样做的意义

生成数据既要快，也要可用。把保存改造与规划迁移分别比较，才能判断收益主要来自减少生成阻塞，还是来自规划方法变化；同时避免用保存条数掩盖任务质量变化。

当前结论

已有结果支持 v1 异步保存改善本任务的生产效率。v2 已完成接口接入与整轮运行，但现有结果没有建立其效率和质量优势。后文先解释改动机制，再用运行记录检验。

03 / 51 · 一、问题与实验设计

时间从哪里开始算，吞吐如何计算

怎么做的

最终就绪时间 T 从第一条 episode 开始计到 output_ready：后台任务已排空、分片已合并、最终输出可用。记录成功吞吐等于保存条数×60/T；末态合格吞吐则将分子换成严格检查通过的条数。

这样做的意义

异步提交可以很快返回，但最终文件可能仍在写入。把终点固定在输出可用时，才能公平比较同步与异步；再用质量通过数作分子，才能回答每分钟真正获得多少合格数据。

当前结论

整批墙钟时间适合衡量生产效率；每个 episode 的阶段均值适合解释等待发生在哪里。多个环境的计时区间会重叠，不能将这些均值或后台写入耗时相加来还原整批时间。

读图与术语

墙钟时间就是现实经过的时间。launcher_seconds 另包含首条任务开始前的启动成本，与本图 T 的起点不同。

原始 v1 使用 MotionGen 规划，主流程同步导出；改进 v1 保留规划和仿真任务，把保存交给 CPU writer；v2 适配版沿用异步保存，改变规划配置、目标类型及结果转换。图中三列对应本项目测试实现。

原始 v1 已经使用 GPU 和多环境仿真。改进 v1 的主要变化是生成与保存能够重叠；v2 的主要变化是规划接口迁移。两项改动应各自对照，不能把保存收益全部归于新版规划库。

沿调用链找到阻塞发生的位置

怎么做的

同步版沿录制器调用进入压缩和 HDF5 写入，返回后继续生成。异步版先由 Bridge.export 打包，再由 ExportPool.submit 提交，writer 后台写分片，主流程通过回执、排空和合并完成收尾；v2 在前端增加 plan_pose 及轨迹转换。

这样做的意义

跟随数据和返回时刻，比只看模块名称更容易理解加速机制：保存从生成控制流中移开后，主流程可以继续准备动作；内存预算不足时仍需等待，保存成本并未消失。

当前结论

改动确实将部分保存工作转交后台，并保留最终输出完成条件。图中箭头表达调用依赖，不表示各框按比例耗时，也不能用来证明 GPU 上的实际重叠。

读图与术语

HDF5 是本实验的数据文件格式；分片是多个 writer 各自写出的中间文件，最终需要合并。

06 / 51 · 二、实现与机制

同步、固定上限与 auto 的差别

怎么做的

workers=0 使用原同步导出。固定上限模式根据待保存任务数按需启动 writer，数量不超过 cap；auto 模式还检查 CPU、内存、I/O 等资源准入，通过后逐步增加 writer。本轮 auto 不主动缩容。

这样做的意义

writer 太少可能积压，太多也可能争抢 CPU、内存和磁盘。固定上限提供简单约束，auto 尝试在有积压且资源允许时扩容，两者影响的是保存侧容量。

当前结论

本轮三种异步配置均实际启动 4 个 writer。因此可以观察异步机制的整体收益，却不能把 cap8 与 cap4 的差异解释成 8 个进程优于 4 个进程，也不能分别量化各项内存改动的贡献。

读图与术语

pending 指尚未完成的保存任务；auto 的资源准入不等于自动增加仿真环境或 GPU。

07 / 51 · 二、实现与机制

生成、移交、写入和合并如何分工

怎么做的

原录制器负责收集 EpisodeData，并调用 HDF5 handler 导出。改进版在生成侧接入桥接层，保存池负责预算、排队与进程管理，writer 接收共享内存描述并写独立分片，主流程最后核对回执和合并文件。

这样做的意义

把职责拆开后，生成不必亲自完成每一次压缩写入；同时，每块数据由谁持有、失败由谁处理也有明确边界，便于定位积压和内存增长。

当前结论

实现已经形成生成主进程与 CPU 保存子进程的分工。这个结构支持流水线重叠，但图本身不提供各模块独立的提速比例；函数映射和冻结源码摘录见 code-structure.html。

读图与术语

共享内存用于让不同进程访问同一块已打包数据；描述信息包含形状、类型及位置，并非重新生成一次轨迹。

08 / 51 · 二、实现与机制

改进如何接入原来的运行流程

怎么做的

启动器 build_source 在内存中构造接入后的运行代码：环境创建前 configure 保存配置，创建后 attach 录制桥接，运行中 poll 处理 writer 回执，结束时 finish 排空并合并。类方法包装和环境实例绑定分别完成接入。

这样做的意义

接入点必须覆盖完整生命周期。只有提交而没有持续回收或最终排空，会造成内存滞留或提前宣布完成；保留独立启动入口也方便比较原始与改进实现。

当前结论

现有实现通过启动注入和运行时绑定接入保存池，上游源码文件没有因此被永久改写。复现实验应使用冻结启动器与相同开关，而非只复制某一个 writer 函数。

读图与术语

hook 指在既有调用点接入包装逻辑；poll 是主流程主动检查后台结果，不是再次保存同一条数据。

09 / 51 · 二、实现与机制

为什么要调整录制缓冲的所有权

怎么做的

改进版让 CPU 图像按环境持有独立数据，避免某个环境的切片继续引用整个批次。打包到共享内存时逐帧移交并释放可回收的源帧；小型 GPU 状态仍先堆叠，再复制到 CPU。

这样做的意义

多环境、长轨迹和多相机会同时保留大量帧。若小切片仍持有大批次底层存储，一个 episode 保存完也未必释放其对应内存，容易抬高峰值并触发预算等待。

当前结论

实现减少了不必要的整批引用保留，但仍存在 CPU 复制和共享内存打包。配对实验观测到内存峰值降低；因为同时改变了保存路径，尚不能将全部下降单独归因于这一项。

读图与术语

所有权指哪一方负责保持数据有效及释放它；切片和独立副本的内存生命周期不同。

10 / 51 · 二、实现与机制

提交成功之后，何时才算保存完成

怎么做的

submit 接受任务后计为 submitted；writer 写完分片并回执后计为 saved；finish 等待所有任务结束，合并、关闭最终输出后才发出 output_ready。失败、超时或 writer 异常退出由主流程处理，并通过 abort 清理资源。

这样做的意义

异步系统同时存在多个完成时刻。如果把提交数当作最终保存数，表面吞吐会很好看，但可能还有未写完数据；异常传播和清理则防止坏任务被悄悄计为成功。

当前结论

本实验以最终输出就绪比较效率，并结合文件回读和质量检查确认结果。后台写入并没有取消数据完整性责任，后续优化也必须保留这条完成链。

读图与术语

output_ready 是整批最终可用标记；saved 是单个保存任务的回执，两者对应不同范围。

11 / 51 · 二、实现与机制

系统中有四种不同的并发

怎么做的

逐段检查执行单位：asyncio 调度多个环境任务；规划和物理算子在 GPU 内部进行数据并行；动作汇合后统一调用批量 env.step；CPU writer 使用独立进程压缩写文件。录制、打包与回执仍由主流程参与。

这样做的意义

这些并发解决不同问题。协程允许任务在等待时交出控制权，GPU 并行处理数值计算，多进程保存利用 CPU 资源；增加其中一种数量，不会自动增加另一种的并行度。

当前结论

明确新增的独立执行者是 CPU writer。规划请求之间、物理与图形引擎之间是否实际重叠，仍需设备时间线确认；源码中的异步接口名称不足以证明重叠。

读图与术语

协程共享主线程，不能让主线程中的同步压缩同时执行；GPU 算子内部并行也不等于多个规划请求同时运行。

12 / 51 · 二、实现与机制

一个生成进程与多个保存进程

怎么做的

历史实验在同一个生成主进程中管理 8 个仿真环境，并调用 GPU 规划、物理和渲染；三种异步配置实际启动 4 个 CPU writer。图中的共享内存连接生成侧与保存侧，结果回执沿反方向返回。

这样做的意义

理解进程边界，可以解释异步保存为何释放生成控制流，也能判断瓶颈是否可能来自 CPU 或磁盘争用，而不是一律归因于 GPU 算力。

当前结论

writer 不启动新仿真环境，也不承担 CUDA 规划。提高保存进程上限是保存侧调度调整；本实验没有验证多个 GPU 生成进程的部署收益。

读图与术语

环境是不同任务状态的仿真实例；进程是操作系统执行单元。8 个环境可以由一个主进程统一推进。

13 / 51 · 二、实现与机制

为什么一个环境的等待会影响整批

怎么做的

各环境任务将动作放入队列；动作数量达到环境数后，主循环执行一次批量 env.step，再通过 task_done 更新队列完成记账。execute 中的 queue.join 等待这些已提交动作被处理。

这样做的意义

统一步进便于批量仿真，却让动作准备和主循环调度成为共同依赖。某个环境尚未提交动作，或主线程正在同步保存，都可能推迟这一批的推进。

当前结论

代码支持主机侧批次等待这一机制解释。queue.join 的等待区间包含主循环完成有用工作的时间，不能直接当作 GPU 空闲；其下降也不能单凭本页分解为某一种设备等待减少。

读图与术语

barrier 指凑齐一批条件后才能继续；队列记账是主机逻辑，不是测量 CUDA 完成时间的设备事件。

14 / 51 · 二、实现与机制

一条数据从录制到释放的生命周期

怎么做的

录制产生源帧；主流程将其打包到共享内存后，可释放不再使用的原 CPU 帧。writer 从共享内存写出分片并发送 saved 回执；主流程收到回执后释放共享内存，并归还在途字节预算。

这样做的意义

生产速度长期快于保存速度时，未完成数据会越积越多。有界预算将积压限制在可承受内存内；正确的释放时刻保证 writer 读取期间数据仍然有效。

当前结论

源帧释放与共享内存释放是两个不同事件。现有流程提供有界积压和完成后回收，代价是预算不足时生成侧仍需等待，不能追求无限排队来换取短期生成速度。

读图与术语

在途数据指已经提交但尚未回收的保存数据；预算限制的是资源占用，不是最终数据集大小。

15 / 51 · 三、v1 效率与耗时解释

异步保存带来了多少最终产出收益

怎么做的

对历史 v1 四组使用相同的 16 条保存目标，读取从首条开始到最终输出就绪的时间，再换算为每分钟保存条数。同步组为基线，cap4、cap8 和 auto 均走异步保存。

这样做的意义

这是用户实际等待结果的指标，包含后台排空和合并，能够检验生成阶段省下的时间是否在收尾阶段又被消耗掉。

当前结论

这轮 8 环境实验中，异步组最终吞吐相对同步提高约 55%–66%，auto 提高约 60.2%。结果支持保存改造有效；各配置只有一轮且实际均为 4 writer，不能据此确定长期最优上限。

读图与术语

耗时减少比例与吞吐提高比例不同：相同产出下，吞吐与时间成反比，不要把两种百分比混用。

16 / 51 · 三、v1 效率与耗时解释

变快之后，数据仍然合格吗

怎么做的

分别统计任务尝试结果、实际保存条数、HDF5 结构回读和严格末态检查。历史 v1 各组 17 个已完成 episode 中有 1 次生成失败，最终保存 16 条；16 条保存数据均通过末态检查。

这样做的意义

只有速度而没有质量约束，可能把提前结束或错误状态计为优化收益。将生成成功和保存后质量分开，才能判断获得的是否是可用训练数据。

当前结论

本轮 v1 各组保存数据均为 16/16 合格，支持观察到的效率收益没有伴随这些检查项退化。样本较小，不能推断所有场景的长期成功率；取消任务也需独立统计。

读图与术语

生成失败计入已完成尝试，但通常不进入成功保存集合；严格末态检查验证最终物理状态，文件结构检查验证数据格式。

17 / 51 · 三、v1 效率与耗时解释

为什么生成完成后还要继续等待

怎么做的

将整批时间分为最后一个已完成 episode 结束之前的生成窗口，以及其后到 output_ready 的尾段。尾段由剩余后台保存、分片合并和文件关闭等工作构成。

这样做的意义

异步保存将工作挪到后台，可以缩短生成阻塞，却可能留下更多收尾工作。观察尾段才能判断端到端收益，避免仅用“最后一条轨迹生成完”作为终点。

当前结论

历史 auto 本轮尾段约 74.48 秒，说明收尾值得继续拆分。它仍在最终吞吐上优于同步；一次较长尾段并不能证明 auto 策略必然导致较差收尾。

读图与术语

尾段按整批独占的墙钟区间计算；后台写入在生成窗口内已经进行的部分，不应再次全部相加。

18 / 51 · 三、v1 效率与耗时解释

episode 阶段均值为什么会下降

怎么做的

从历史已完成 episode 日志中分别取规划、execute、导出或入队等阶段，计算每组均值；v1 各组统计 17 个完成尝试，包括一次失败。异步入队与同步完整导出的工作范围在图中分别标注。

这样做的意义

整批收益需要用阶段变化解释。保存工作占用主控制流时，其他环境可能仍处于 execute 等待中；移走保存工作既能改变导出阶段，也可能缩短观察到的执行等待。

当前结论

同步导出均值约 25.6 秒，auto 入队约 2.6 秒，但后者还不包含后台写入完成。execute 均值的下降支持主循环受阻减少的解释；内部具体归因由第 29–32 页的插桩配对补充。

读图与术语

阶段均值用于比较同类区间；多个环境会重叠，不能将这些条形累计成整批最终时间。

19 / 51 · 三、v1 效率与耗时解释

execute 计时到底覆盖什么

怎么做的

历史计时器包住整个 await execute 调用：准备或提交动作后，等待动作队列的完成条件。此时主循环可能在推进其他环境、调用物理、更新观测，甚至执行同步导出。

当前结论

读图与术语

读图与术语
