效率优化报告 · 2026 年 10 月 14 日

从导出瓶颈、录制内存所有权到有界共享内存，围绕 12 组图表梳理已完成的实验、数据结构改动和验收边界。

先看结果

8 环境、每模式 24 条的已有 GPU 对照中，双写入进程将最终文件就绪时间从 1156.74 秒缩短到 891.22 秒，耗时减少 23.0%，对应吞吐提升 29.8%。生产进程峰值 RSS 从 56.2 GiB 降到 40.7 GiB。

收益来自导出并行与内存所有权调整的组合。gzip-2、HDF5 字段、帧序和成功标签保持原有规则。严格物理回读在三种模式中均为 23/24，整体物理验收仍未通过；历史 100 条目标也未完成。

01

先把不同实验放回各自的问题里

共享配置探针回答“两端能否按同一规则启动和判断成功”；早期 1 环境与 4 环境测试回答“生成链路是否能产出可回读轨迹”。随后 8 环境、100 条目标运行暴露了规模问题：63 次开始、55 次完成，遥测成功 49、失败 6，剩余 8 次结果未知。子进程 SIGKILL，cgroup 的 oom_kill 增加 1，进程峰值 RSS 约 66.6 GiB。该 cgroup 包含其他进程，仅凭这些记录不能锁定受害进程。

异步初版也出现过 SIGKILL 和 OOM 计数增加。之后才定位并修复跨环境 CPU 视图保留整批存储的问题。最终对照的三种模式各保存 24 条、32,959 帧，OOM 计数均没有增加。图中不同轮次不可合并成统一成功率，也不能把 24 条对照当作 100 条生产验收。

02

导出瓶颈落在 RGB 建数据集阶段

左图中，轨迹堆叠约 0.230 秒，CPU / NumPy 约 0.000334 秒，HDF5 flush 约 0.00419 秒；建数据集占总导出时间 98.7%。右图将三路 RGB 拆开，左腕、右腕和第三视角分别约 11.12、4.15、10.56 秒。优化应优先处理 RGB 的压缩与 chunk 写出成本。

这里的 dataset_create 同时包含压缩、HDF5 处理和 I/O；它不是纯磁盘耗时。建数据集的线程 CPU 时间与墙钟接近，支持 CPU 计算成本较高的判断。离线数据已在 CPU，因此极短的 cpu_numpy 时间不能证明在线 GPU 传输没有成本。write_episode_inclusive 是嵌套计时，未加入阶段总和；flush 也不表示数据已物理落盘。

gzip-2 建数据集约 25.75 秒、输出约 525 MiB；LZF 约 16.98 秒、796 MiB；无压缩约 10.10 秒、3545 MiB。无压缩输出约为 gzip 的 6.75 倍。当前方案保留 gzip-2，把 CPU 写出移入独立进程，以控制存储增长和格式变更。

另有 32 帧 × 三路 RGB、每方式 3 次的轮换顺序对照，可用于局部复核。文件写入字节数不同、页缓存可能已预热，差值不能精确隔离出 gzip 的纯耗时。无压缩连续存储的另一轮回放为 0.859 秒，但 chunk 策略也改变了，不能和图 4 当作同口径比较。

03

改变内部所有权与传输结构，保留输出契约

同步模式仍为默认入口。启用异步后，生产者把完成的回合打包到共享内存；队列只传路径、形状、dtype、偏移和元数据描述符。CPU worker 使用 spawn，各自拥有 HDF5 分片，避免多个进程共享一个活动 HDF5 句柄。提交时分配 demo ID，完成顺序不会重排同一回合的帧、动作和观测。

队列按字节预算约束，排队和正在写入的共享内存都计入预算；满载时生产者等待，单条超过预算会明确失败。worker 写完并 ACK 后才释放共享内存。最终等待全部 ACK、关闭分片，再复制压缩组、核对结构与计数，并发布独立文件。失败时保留分片和清单供诊断。

旧录制方式先 clone 整个环境 batch，再把某环境的切片放入其回合。切片仍引用原 batch 的底层存储：一个环境仍需要该帧时，其他环境对应的存储也可能无法释放。异步新路径对 CPU 帧按环境 clone，建立独立所有权；移交时逐帧写入共享内存并释放原帧，周期性将 glibc 空闲页归还系统。

对图 3 的 1342 帧轨迹，三路 640×480×3 uint8 RGB 的未压缩体积为 3,710,361,600 字节，约 3.46 GiB。这是按形状计算的 RGB 体积，不是 RSS 实测。一次多保留整条副本就可能新增数 GiB 压力。新路径避免生产者对整条 RGB 再做完整 stack；小型 GPU 状态字段仍按字段堆叠后一次转到 CPU，减少逐帧同步。

双 worker 的生产阶段吞吐提升约 46.1%，但最终文件吞吐提升为 29.8%，完整启动器吞吐提升为 28.3%。最终文件就绪从首回合开始计时，包含排空、合并和关闭；完整启动器还包含启动与结束。报告主结论使用最终文件口径，避免只看“生成结束”而遗漏导出尾部。

单 worker 的累计入队等待约 222.43 秒，双 worker 为 80.96 秒；收尾排空从 104.95 秒降至 53.18 秒。单条 worker 写出均值却接近：26.63 与 26.83 秒。观察支持“通过并行提高服务能力、减少阻塞”的解释，而不是单次压缩算法提速。

双 worker 的合并耗时反而从 7.09 秒升至 44.42 秒。现有单轮记录无法确定原因，分片布局、缓存和系统 I/O 状态均需进一步测量。两种模式都要计入合并，后续增加 worker 也必须同时观察排空与合并，而不是假设吞吐线性增长。

05

内存收益成立，但队列预算不是整机上限

生产进程峰值 RSS 为 56.2 / 40.5 / 40.7 GiB，双 worker 相对同步下降约 27.6%。cgroup 采样峰值约 56.0 / 40.1 / 41.4 GiB，是另一种范围与采样口径，不能与进程 RSS 或队列内存相加。最终三轮 OOM 计数增量均为 0。

异步队列峰值为 14.44 GiB，低于 16 GiB 配置上限，占约 90.2%。这个预算包含待写和在写共享载荷，不包含活跃环境的录制缓冲、模拟器、worker 私有内存和系统缓存。多个进程 RSS 还可能重复统计共享页，因此评估物理压力应结合 cgroup 与系统可用内存。

整卡显存峰值从约 15.6 GiB 升至约 18.5 GiB。它不是当前进程独占显存，现有记录不足以将增长完全归因于某个代码改动。方案减少了 CPU 内存保留，却没有证明所有资源占用均下降。部署时仍须预留 /dev/shm 和系统内存，并持续观察显存。

06

离线回放验证搬运，GPU 对照验证在线收益

离线 4 条固定数据：同步、单 worker、双 worker 最终就绪分别为 105.13、105.45、56.66 秒。单 worker 提交只需约 4.58 秒，但最终文件没有变快；只计提交时长会显著夸大收益。双 worker 离线吞吐提升约 85.6%，在线收益为 29.8%，因为仿真、规划、执行和录制也占用时间。

每种 GPU 模式目前只有一轮正式对照，存在执行顺序、页缓存和系统负载差异，且没有误差条或多轮统计区间。29.8% 是这组记录的描述性结果；同步与异步同时改变导出调度和 CPU 帧所有权，现有证据不能单独量化两项改动各自的因果贡献。

07

格式兼容已经验证，物理质量仍有缺口

三种模式都标记并保存 24 条成功轨迹，HDF5 格式检查通过；严格最终状态检查都只有 23 条通过。共同失败的 demo_2 已在垫内、夹爪已释放，但终态线速度约 0.2108 m/s、角速度约 5.7481 rad/s，分别约为允许阈值的 7.03 与 11.50 倍。成功标签与最终物理状态出现不一致，须在接受数据前解决。

这个结果说明失败在三个模式中共同存在，且非 RGB 对照没有发现异步搬运改变轨迹数据；它不等于证明所有物理与标注质量都已正确。这里未修改阈值、轨迹数据或成功标签，也未把未通过样本剔除后重新包装成全量通过。

源数据来自 replay fixture，阶段标注为推断结果，未经过人工审核。被动右腕视角在该左臂任务中可能接近黑图，结构有效不等于视觉信息充足。右臂没有实际可用生成源，因此本报告不包含右臂生成成功结论。历史共享配置 v003 的源文件当前也不齐全，其探针结果保留为历史证据。

08

下一轮先闭合质量与规模验收，再扩展并行度

顺序工作判断依据
1 · 修复质量闭环定位 demo_2 的成功判断、最终保持与录制终点；新增证据保留旧记录严格终态全量通过；成功标签与回读一致；阈值不放宽
2 · 重跑规模目标在独立 GPU 环境用新路径执行 100 条目标；默认同步仍可回退生成数、submitted、saved、文件回读一致；排空合并完成；资源无异常
3 · 验证收益稳定性轮换 0 / 1 / 2 worker 顺序，增加重复；记录负载与缓存条件分别报告生产、最终文件、完整启动器吞吐和波动
4 · 继续优化尾部检查分片布局、合并 I/O、背压与 16 GiB 队列余量在同样质量和压缩条件下减少排空 / 合并总尾部
5 · 再评估格式策略仅在存储预算明确后评估 LZF / chunk 调整同时比较写入、体积、训练读取和旧 loader 兼容性

基于当前单组对照，双 worker 是后续验证的候选配置：8 环境、16 GiB 导出队列、600 秒超时、gzip-2。它还不是百条生产验收通过的配置。共享配置与版本整理降低了复现和排查的复杂度，但没有独立工时测量，本报告不为这类改动虚构百分比收益。
